RPG WEAPON PAWNSHOP - CORE SYSTEM SPECIFICATION
Version: Draft 0.2
Purpose: Codex implementation handoff
Target: Godot 4.6.1 / GDScript prototype
Scope: Weapon-only prototype / guest generation / weapon generation / appraisal / purchase negotiation / reputation loop

This file supersedes Draft 0.1.

======================================================================
0. IMPLEMENTATION INTENT
======================================================================

This is a fantasy RPG weapon pawnshop game.

Core loop:
1) Generate one guest.
2) Generate one weapon owned by that guest.
3) Store the weapon's TRUE internal data.
4) Show only player-known information.
5) The player uses appraisal actions to reveal hidden information.
6) The system calculates the weapon's TRUE current appraised market price.
7) The guest calculates a customer asking price from purpose + market knowledge.
8) The player chooses a purchase offer.
9) The guest accepts / counters / rejects according to purpose and negotiation rules.
10) On transaction completion, calculate satisfaction.
11) Update shop reputation and successful trade count.
12) These shop-state values affect future guest quality.

Prototype priority:
- Data flow must be correct and testable.
- Balance values must be data-driven and easy to replace.
- Build a working simulation before polished UI/art.

OUT OF SCOPE FOR FIRST PROTOTYPE:
- Armor and accessories as tradable items.
- Ego weapons, named weapons, cursed weapons, discontinued weapons.
- Shop decorations.
- Full resale-to-buyer system.
- Full order/request system.
- Story content.

IMPORTANT:
Do not invent new mechanics just to fill missing balance details.
For unfinished numeric tables, use explicitly marked TEMPORARY prototype config values.

Use English-only filenames and paths.
Use snake_case for code variables and data keys.


======================================================================
1. CORE TERMINOLOGY: VALUE VS PRICE VS PLAYER INPUT
======================================================================

The implementation MUST separate the following concepts.

A) INTERNAL VALUE MODIFIERS
These are dimensionless decimal modifiers used by the price formula.
Examples:
value_normal_stat = +0.50
value_reinforce = -0.20
value_class_popularity = +0.20

B) TRUE ITEM DATA
The actual stats and state owned by the generated weapon.
Examples:
actual_strength = 42
actual_attack = 67
actual_crit_chance = 7.4
actual_refining_level = 8
actual_stability = 46

C) PLAYER-KNOWN DATA
What the player has successfully discovered through appraisal.
This is separate from TRUE item data.

D) PRICES
Gold amounts.

base_price
    Tier-based base price before item modifiers.

true_appraised_price
    The system's hidden true current market appraisal of the weapon.
    This is NOT automatically shown to the player.

customer_asking_price
    The price the guest asks for.

player_purchase_offer
    The amount chosen/input by the player.

final_purchase_price
    Equals player_purchase_offer only if the guest accepts it.

IMPORTANT:
There is NO variable named player_appraisal_value in the first prototype.
The player judges value by looking at revealed item information and choosing an offer.
The system's true appraisal and the player's judgment must never be merged.

======================================================================
3. STORE STATE
======================================================================

3.1 shop_reputation
-------------------
Type: int
Initial value: 0

Meaning:
Long-term reputation of the shop.

Effects:
- Higher shop_reputation increases the probability of higher guest_level.
- Higher shop_reputation increases the probability of higher guest_power.
- It does NOT directly modify weapon price.

Base reputation changes after a completed negotiation result:
VERY_SATISFIED = +6
SATISFIED      = +2
DISSATISFIED   = -4
HUMILIATED     = -8

If player refuses / does not purchase the offered item:
50% -> 0 reputation
50% -> -2 reputation

Future order system, NOT required for initial prototype:
Order completed: +20
Order failed: 50% -> -10, 50% -> -30


3.2 shop_trade_count
--------------------
Type: int
Initial value: 0

Meaning:
Total count of successfully completed purchase transactions.

Increment:
+1 only when a purchase succeeds.

Effects:
- Higher shop_trade_count increases probability of higher guest_title.
- Higher shop_trade_count increases probability of higher guest_achievement.

Do NOT call this shop_sell_count.

4. RANDOMNESS POLICY
======================================================================

All random generation must be seedable for debugging.
Use weighted_choice() for weighted tables.
Use uniform_choice() for exact equal-probability categories.

Validate all probability tables during development.
- No negative weight.
- Sum should be 1.0 within a small floating-point epsilon.
- Log invalid tables instead of silently accepting them.

EXACT UNIFORM RANDOM VARIABLES:

4.1 guest_class
6 possible values, exactly equal probability:
WARRIOR = 1/6
MAGE    = 1/6
ROGUE   = 1/6

4.3 guest_knowledge
3 possible values, exactly equal probability:

SOME = 1/3

4.4 guest_purpose
3 possible values, exactly equal probability:
EMERGENCY_CASH   = 1/3

IMPORTANT:
These four variables are independent uniform rolls unless a future design explicitly changes them.
Do not make their weights depend on shop reputation or trade count.

NOT UNIFORM BY DESIGN:

- guest_power depends on shop_reputation.

======================================================================
6. WEAPON COMPATIBILITY AND TARGET CLASS
======================================================================

6.1 compatibility roll
----------------------
After guest_class is generated:

80% -> weapon is usable by guest_class
20% -> weapon is not usable by guest_class

Variable:
is_class_compatible: bool

If true:
- Select item_type uniformly from guest_class weapon pool.
- item_target_class = guest_class.

If false:
- Select item_type uniformly from all weapon types NOT usable by guest_class.
- Determine all classes that can use the selected item_type.
- Select item_target_class uniformly from those compatible classes.

Why item_target_class exists:
- class_power / class_popularity must refer to the class whose market uses the item.
- shared weapon types such as staff need an explicit target class.
- actual relevant stats also depend on the intended class build.

For incompatible weapons:
- guest_power does not define their stat quality.
- other guest progression variables may also eventually use alternate loot rules.
- Keep incompatible-item generation modular.

9. CONCRETE RPG STAT SYSTEM: TRUE DATA VS PLAYER-KNOWN DATA
======================================================================

9.1 design rule
---------------

Internal words such as EXCELLENT, ADEQUATE, LOW, MIXED and HIGH are for generation,
balance and price calculation.

Normal player-facing item UI should instead show concrete RPG-style information such as:

STR +42
Attack +67
Critical Chance +7.4%
Refining +8
Stability 46%

The exact numeric stat is generated FROM the internal grade and item tier.
Therefore:

internal grade -> true numeric stat -> appraisal reveal -> player-known stat

The true numeric stat and the player-known stat are separate data.

IMPORTANT PRICE RULE:
The current price formula uses the INTERNAL GRADE value modifiers.
Do NOT also add the generated numeric stat to the price formula.
That would double-count the same quality information.

Numeric stats are the concrete manifestation of the already-generated internal grade.

9.5 numeric generation rule
---------------------------

Use configurable numeric-range data.
Do not hardcode ranges inside UI or generator scripts.

General formula for a relevant NORMAL/HIGH stat:

actual_value
=
round(
    tier_reference_value
    * random_uniform(grade_multiplier_min, grade_multiplier_max)
)

Prototype TEMPORARY reference values:

NORMAL STAT tier_reference_value:
T1 = 10
T2 = 18
T3 = 30
T4 = 48
T5 = 72

HIGH STAT tier_reference_value:
T1 = 12
T2 = 22
T3 = 38
T4 = 60
T5 = 90

TEMPORARY NORMAL grade multiplier ranges:
MIXED     = 0.35 - 0.55
ADEQUATE  = 0.70 - 0.90
EXCELLENT = 1.00 - 1.20
NONE      = no relevant normal-stat line

TEMPORARY HIGH grade multiplier ranges:
LOW       = 0.35 - 0.55
ADEQUATE  = 0.70 - 0.90
EXCELLENT = 1.00 - 1.20
NONE      = no relevant high-stat line

These numeric values are prototype display values, NOT final balance.
Put them in a config resource so they can be changed without code edits.


9.6 visual meaning of NORMAL grade
----------------------------------

Use item_target_class to identify the relevant primary normal stat.

EXCELLENT:
- Generate relevant primary stat using EXCELLENT numeric range.

ADEQUATE:
- Generate relevant primary stat using ADEQUATE numeric range.

MIXED:
- Generate relevant primary stat using MIXED numeric range.
- Also generate one random non-primary normal stat line at a lower/medium amount.
- This visually communicates that part of the stat budget is wasted.

NONE:
- Do not generate the relevant primary normal stat.
- Optional: generate one irrelevant normal stat line using a low temporary range.

This is a presentation/data-generation rule.
Price still uses value_normal_stat from Section 8.


9.7 visual meaning of HIGH stat grade
-------------------------------------

Use item_target_class to determine whether ATTACK or MAGIC_POWER is relevant.

EXCELLENT:
- Generate relevant high stat using EXCELLENT range.

ADEQUATE:
- Generate relevant high stat using ADEQUATE range.

LOW:
- Generate relevant high stat using LOW range.

NONE:
- No relevant high stat.
- Prototype option: 50% no high-stat line, 50% generate the opposite high-stat type as a wasted stat.
- Keep this 50/50 value configurable.

Price still uses value_high_stat from Section 8.

Generation probability and class relevance table are not finalized.

Do not invent a permanent class-special-stat system.


9.10 amplification concrete lines
---------------------------------

Amplification is displayed as concrete extra normal-stat lines.

Possible normal stat IDs:
strength
dexterity
luck
intelligence
divine_power

UNAPPLIED:
- amplification system has not been assigned/used.
- no lines exist.
- still has +0.20 appraisal value because future potential remains.

ZERO_LINE:
- amplification was applied but produced no useful needed-stat line.

ONE_LINE / TWO_LINE / THREE_LINE:
- generate exactly that many assigned amplification lines.

LOW/HIGH controls line strength using configurable numeric ranges.

TEMPORARY prototype line-value rule:
Use NORMAL tier_reference_value from Section 9.5.

LOW amplification line:
10% - 20% of tier reference value

HIGH amplification line:
20% - 35% of tier reference value

Line stat IDs may be random among the five normal stats.
The appraisal grade already represents whether the resulting line combination is valuable.
Do not recalculate price from the exact line numbers in the first prototype.

    internal_grade
    applied_scroll_count
    successful_scroll_count
    scroll_profile_ids
}

Exact scroll counts/types are not finalized.
For the first prototype, a debug-readable text summary is sufficient.
Keep the structure extensible.

actual refining level = integer 0-10.

Player-known value may be:

9.13 stability player-facing data
---------------------------------

Store true stability as exact integer:

Derive pricing bracket from actual_stability:

60-79                -> STABILITY_60_PLUS
40-59                -> STABILITY_40_PLUS
20-39                -> STABILITY_20_PLUS
0-19                 -> STABILITY_BELOW_20

Player-known stability may be UNKNOWN / RANGE / EXACT.

Example after successful appraisal:
Stability: 46%

Exact stability consumption from reinforcement/refining/amplification is TODO.

10. MARKET STATE
======================================================================

Each class has two weekly market variables:
class_power
class_popularity

At game start, prototype default:
all class_power = NORMAL
all class_popularity = NORMAL

Every 7 in-game days, independently reroll each class variable.

class_power states, uniform probability:
STRONG = 1/3
NORMAL = 1/3
WEAK   = 1/3

Value:
STRONG = +0.15
NORMAL = +0.05
WEAK   = -0.10

class_popularity states, uniform probability:
POPULAR   = 1/3
NORMAL    = 1/3
UNPOPULAR = 1/3

Value:
POPULAR   = +0.20
NORMAL    = +0.05
UNPOPULAR = -0.20

For weapon pricing, read market state from item_target_class.
Do NOT automatically use guest_class for an incompatible weapon.

Future systems may add patch previews, trends, rumors, or persistence.
Not required now.


======================================================================
11. STABILITY PRICE MULTIPLIER
======================================================================

Stability is permanent processing headroom, NOT ordinary durability.
It does not decrease from normal weapon use.
It is primarily consumed by reinforcement/refining/amplification.

First calculate true_item_value_modifier BEFORE stability.

If true_item_value_modifier < +2.00:
actual_stability = 100    -> multiplier 1.50
80-99                     -> multiplier 1.30
60-79                     -> multiplier 1.00
40-59                     -> multiplier 0.80
20-39                     -> multiplier 0.60
0-19                      -> multiplier 0.40

If true_item_value_modifier >= +2.00:
actual_stability = 100    -> multiplier 2.00
80-99                     -> multiplier 1.60
60-79                     -> multiplier 1.20
40-59                     -> multiplier 1.00
20-39                     -> multiplier 0.90
0-19                      -> multiplier 0.60

Variable:
stability_multiplier


======================================================================
12. TRUE APPRAISAL PRICE FORMULA
======================================================================

12.1 effective refining value
-----------------------------

effective_refining_value
=
value_refining
*
(
    0.4 * coefficient_normal_stat
    +
    0.6 * coefficient_high_stat
)


12.2 true item value modifier
-----------------------------

true_item_value_modifier
=
value_class_popularity
+ value_class_power
+ value_normal_stat
+ value_high_stat
+ value_special_stat
+ value_unique_stat
+ value_reinforce
+ value_amplification
+ effective_refining_value

NOTE:
Do not include a leading +1 inside true_item_value_modifier.
The +1 is applied in the price equation below.


12.3 raw appraised price
------------------------

raw_appraised_price
=
base_price * (1 + true_item_value_modifier)


12.4 stability application
--------------------------

appraised_price_before_floor
=
raw_appraised_price * stability_multiplier


12.5 minimum floor
------------------

minimum_price = base_price * 0.10

true_appraised_price
=
max(appraised_price_before_floor, minimum_price)

Round displayed/debug gold values to integer gold.
Internally, calculation may use float until final rounding.

IMPORTANT:
true_appraised_price is internal hidden truth.
Do not show it automatically in normal player UI.


======================================================================
13. CUSTOMER ASKING PRICE
======================================================================

purpose_price_multiplier:
EMERGENCY_CASH   = 0.50
UPGRADE_PURCHASE = 0.80
GREEDY_SELLING   = 1.00

knowledge_price_multiplier:
NONE = 1.00
SOME = 1.10
HIGH = 1.20

normal_customer_asking_price
=
true_appraised_price
* purpose_price_multiplier
* knowledge_price_multiplier

SCAMMER override:
customer_asking_price
=
max(
    normal_customer_asking_price,
    true_appraised_price * 1.50
)

Non-scammer:
customer_asking_price = normal_customer_asking_price

Round to integer gold for display.


======================================================================
14. PLAYER PURCHASE OFFER AND FINAL PRICE
======================================================================

player_purchase_offer:
- Direct player input/choice.
- Must be >= 0.
- Must not exceed current player cash unless a future credit system exists.

If accepted:
final_purchase_price = player_purchase_offer
shop_trade_count += 1

If rejected:
final_purchase_price = null
shop_trade_count does not increase.

Do NOT automatically calculate final_purchase_price from true_appraised_price.


======================================================================
15. NEGOTIATION AND SATISFACTION
======================================================================

Define:

offer_ratio
=
player_purchase_offer / true_appraised_price

Use guest_purpose thresholds from Section 5.9.

Acceptance / counteroffer / rejection logic is not completely finalized.

Prototype minimum behavior:
- If player_purchase_offer >= customer_asking_price: accept immediately.
- Otherwise, if negotiation attempts remain: allow counter/retry.
- If no attempts remain: reject unless future minimum-acceptance config says otherwise.

Keep all thresholds data-driven.

Kindness satisfaction override:
GENEROUS:
- cannot end as HUMILIATED; convert HUMILIATED -> DISSATISFIED.

NORMAL:
- cannot end as HUMILIATED; convert HUMILIATED -> DISSATISFIED.

ARGUMENTATIVE:
- no current satisfaction override.

RUDE:
- no satisfaction override; reputation receives -2 later.

SCAMMER:
- use special scam behavior.


======================================================================
16. REPUTATION UPDATE
======================================================================

Base delta:
VERY_SATISFIED = +6
SATISFIED      = +2
DISSATISFIED   = -4
HUMILIATED     = -8

Then apply guest_kindness modifier:
GENEROUS      -> +2
NORMAL        -> +0
ARGUMENTATIVE -> +0
RUDE          -> -2

SCAMMER failed-demand special case:
current delta = -5
unless later anti-scam mechanics override it.

Finally:
shop_reputation += final_reputation_delta
